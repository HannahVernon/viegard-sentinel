- [ ] **Slow-loris / incomplete-request handling (class of problem, DECISION DEFERRED 2026-09-22)**: observed a Require-approval decision (severity 6, category `vulnerability-scanner`) driven by a SINGLE HTTP event: status `408`, `BodyBytes 0`, `RequestSeconds 60.029`, source `34.74.125.239` (looks like Google Cloud), host `www.sqlserverscience.com`.  A 408 with 0 body and a request time at the server timeout is an incomplete/stalled request; on its own it is weak evidence (no method/URI/User-Agent is present because the request line never completed, so intent cannot be confirmed).  A single stalled connection is also inert as an attack - slow-loris needs many concurrent held connections, each of which logs its own 408 on timeout.  So the real signal is `K` qualifying events (`StatusCode == 408` AND `BodyBytes == 0` AND `RequestSeconds >= floor`) from one source within a window `T`, not one event.
  - Immediate observation (not yet actioned): a lone 408 is currently over-weighted (scored to severity 6).  Whatever the chosen path, a single incomplete request should be low-weight and only a burst should escalate.
  - **Path A - reweight and accumulate (minimal):** give a lone incomplete-request a low per-event weight, below the review gate, and let `K` of them sum past it inside the existing source-IP-keyed incident (`TimeWindowCorrelator` already groups HTTP events by `ip=` over a sliding window); count-aware confidence (D-0050) adds volume confidence.  Reuses shipped machinery.  Caveats: it is a linear sum, not a strict "K within T" counter; the incident window slides as events arrive; and `MaxEvidenceItemsPerIncident` / `MaxEventIdsPerIncident` caps and evidence truncation must not neuter a large burst.
  - **Path B - explicit windowed burst detector (more correct, more work):** a stateful counter keyed by (source, signal) that fires a distinct `connection-exhaustion` / `slow-loris` category only once `K`-within-`T` is reached; precise and reusable for other bursts.  This is the "Rate-based burst detection (propose-only)" foundation below; slow-loris becomes one consumer of it once a path is chosen.
  - **Cross-cutting (either path):** config-owned + Admin-UI + API thresholds per the D-0029 pattern (qualifying status set incl. maybe `499`, `RequestSeconds` floor, `BodyBytes == 0`, `K`, `T`, propose-only vs action-eligible); verified-crawler / uptime-monitor allowlist via forward-confirmed rDNS; caution on NAT / shared-egress IPs; propose-only first; calibrate `K`/`T` from the real 408-per-IP-per-window distribution before hard-coding (baseline currently unknown - needs a query against the events DB with the project owner's approval).
  - **Out of scope note:** per-source counting does not catch DISTRIBUTED slow-loris (a botnet holding one connection each from many IPs); that needs a global 408-rate signal that cannot be actioned by IP-banning.  Decide separately whether that is in scope.
